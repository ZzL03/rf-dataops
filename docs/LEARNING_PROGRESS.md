### 2026-10-26：M0 持久保存理解与任务领取

- 学习者回答：“不会丢失，因为任务信息保存在了数据库中，数据库不会因为API进程重启而丢失，worker仍能从数据库中领取任务。”
- 评价：正确理解任务记录独立于 API 进程内存；能联系 Worker 从同一数据库领取任务的架构。
- 条件澄清：数据库仍可用且任务已经成功提交，Worker 为独立运行的进程；未将此结论扩大为数据库故障也不会丢数据。
- 本轮教师定位：`Worker.run_once` 的 `claim` 调用，`JobQueue.claim` 的候选条件、状态/执行者更新与返回 token；没有可领取任务时返回 None，并在主循环中等待再查询。
- 待思考：若 Worker 仅查询 PENDING 任务后就执行、不将其改为 RUNNING，多个 Worker 同时运行时可能发生什么？

### 2026-10-26：M0 查询失败与任务失败的边界

- 学习者回答摘要：不能认定失败，因为轮询有次数上限，未达到上限不会直接判定失败；轮询给 Worker 留处理时间，到上限再提示检查。
- 准确部分：浏览器暂时断网不能证明后台任务 FAILED；页面确实存在轮询上限提示。
- 需修正：判断依据不是次数。网页查询与 Worker 执行独立；达到上限也不把任务改为 FAILED，未达上限也可能查询到真正的 FAILED。
- 源码核对：`AssetCenter.poll` 先检查返回的 SUCCEEDED/FAILED，再判断 attempts；请求异常进入 catch，清空本页 activeJob 并显示错误，没有安排下一次轮询，也没有修改数据库任务状态。
- 可靠性边界：当前扫描页未在该 catch 中实现网络异常后自动重试；不能将正常轮询描述为网络失败重试。
- 待复验：若第 2 次成功查询返回 FAILED，是否仍要等到轮询上限？请解释判断依据。
