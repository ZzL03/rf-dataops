# RF-DataOps：演示与面试讲解

## 五分钟演示

仓库根运行 `python scripts/quickstart.py --demo`。打开18080工作台，用本地
artifacts/demo-accounts.json里的账号登录。数据与类别操作均为合成演示，不介绍模型准确率。

1. 数据资产：搜索报告artifacts/phase5-demo.json中的batch，展示BIN/HDF5元数据、完整SHA-256、
   片段数和接入历史。解释区间索引只保存起点/长度，不复制所有片段。
2. 后台任务：查看SCAN、SEGMENT、QUALITY、INFER、PUBLISH状态、尝试次数、执行版本和事件。
   强杀恢复与过期提交的证据来自自动化故障测试，不靠演示时随机kill进程。
3. 人工审核：展示波形、频谱、Mock版本与人工历史。说明预测与人工标签不同表，提交携带版本号，
   两人冲突返回409，前端保留草稿。可以用两个浏览器登录会话亲自演示冲突。
4. 数据集：报告里的RF-Demo版本v1.0.0有4个QPSK演示标签；v1.0.1为1个BPSK和3个QPSK。
   下载两份Manifest，指出v1仍是原标签、原人工历史ID，清单含完整源/区间/处理/模型来源。
5. 展示TESTING.md和具体测试源码，再说明单任务上限、原始文件留存和真实模型仍需验证的边界。

## 常见追问

**为什么用PostgreSQL队列？** 当前业务规模下可让正式业务结果和任务成功同事务提交，避免引入
第二个状态权威和跨系统双写。代价是轮询、历史增长、优先级饥饿及吞吐上限；未来可评估外部队列与Outbox。

**行锁会不会锁整个推理？** 不会。领取是短事务，提交后读取和计算；心跳使用独立Session。
结果提交另开事务校验执行令牌。SKIP LOCKED让其他Worker跳过被锁任务，不保证严格FIFO。

**Worker被kill后怎么恢复？** 租约过期后转RETRY_WAIT或最终FAILED，重新领取递增执行版本。
旧Worker不能续租或发布结果。最大次数包含第一次；手工重发是新generation，不改旧失败记录。

**为什么最后还要检查租约？** 提交开始时有效，不代表业务写完后仍有效。最终条件UPDATE是
成功提交的决定点，失败必须回滚已经插入的正式结果。已有测试在业务写完后让租约过期验证这一点。

**算不算exactly-once？** 只能保证至少一次计算、受令牌保护的幂等发布；允许崩溃后重复计算。
唯一约束、同令牌/同语义摘要重放和事务回滚共同防重复正式结果，不能称为严格只执行一次。

**如何防止两人覆盖标签？** UPDATE带expected_version，成功才同事务追加历史和当前指针。
零行表示冲突，返回409。前端不能静默改成最新版本重提。

**为什么发布用REPEATABLE READ？** 筛选成员、标签和配置需要同一个一致视图。否则分多次查询
可能混入并发修改。发布保存具体历史ID及冻结内容，下载不再拼接当前标签。

**仅禁止UPDATE/DELETE够不够？** 不够，别人还可能追加新成员。因此成员INSERT也锁父版本，
检查未封存且创建事务相同；提交时必须已封存。直接SQL和并发追加均有实际拒绝测试。

**Manifest为什么放数据库？** 文本、成员和任务状态可以共同原子提交，下载返回确切历史字节。
大规模导出包若要落磁盘，应另设计唯一临时输出、不可变引用、失败清理或Outbox，不能靠rename宣称SQL双写原子。

**数据库快照能保证IQ永久不变吗？** 不能。它固定引用和校验值，不能阻止宿主机改写或删除文件。
当前依赖完成后不再写入的协议、只读挂载、完整哈希与留存；真正的物理留存需存储快照或归档。

**Mock模型有什么价值？** 验证工程合同、后台调度、版本、权限、审核和发布。它的分数没有识别
准确率含义。真实模型需提供可信权重、网络/输入布局、预处理和类别顺序，再补加载/精度/性能验证。
